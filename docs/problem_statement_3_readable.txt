PS-003 Small Web Reader: Anonymous Discovery for Independent Blogs Background: Most people read the web through algorithmic feeds that decide what they see. RSS and Atom are the older alternative: you follow blogs directly, with no ranking, ads or tracking. The weak spot is discovery, since feed readers assume you already know which blogs you want. One way to fix this without an algorithm is to look at overlap between readers. If many people who follow blog A also follow blog B, B is probably worth a look. That only needs a shared server that counts which feeds are followed together, with no accounts or tracking. Build a feed reader that lets people follow blogs, read full articles even offline, and discover new blogs through anonymous recommendations. Tasks A) Build the Reader Create a single full-stack web application with two layers: 
-  Client ○ A web UI with a unified timeline, a subscriptions list, a reading view and a Discover page. ○ All feed parsing, article extraction and caching happen in the browser. 
-  Server (same app) ○ Fetch route: takes a URL and returns the raw response, since browsers can’t fetch most feeds or pages directly because of CORS. It must not parse or store content. ○ Discovery API: a database-backed service that collects anonymous subscription data, ranks feeds and serves recommendations. B) Client-Side Feed Handling 
-  Autodiscovery: Given a site URL, find its feed via <link rel="alternate"> or common paths such as /feed and /rss.xml . 
-  Parsing: Support RSS and Atom, and show posts in one chronological timeline. 
-  Reading state: Mark posts read or unread, and filter by feed. 
-  Resilience: Handle dead feeds, malformed XML and slow servers without breaking the timeline.

C) Full-Text Reading 
-  Fetch the original article through the fetch route, extract the main content (e.g., Mozilla Readability) and show it in a clean reading view. 
-  Sanitize all extracted HTML before rendering (e.g., DOMPurify). Unsanitized proxied content is a security failure. 
-  Fall back gracefully to the feed’s own summary when extraction fails. D) Anonymous Discovery (Core Technical Challenge) 
-  No accounts, no persistent IDs. Sharing is opt-in. When enabled, the client submits its subscription list as a single anonymous batch. 
-  Ranking combines popularity (how many clients follow a feed) and co-subscription (feeds frequently followed together with the user’s own). A simple database query is enough. 
-  API: submit subscriptions, get recommendations for a given set of feeds, and get popular feeds. Recommendations never include feeds the user already follows. 
-  Integrity: ○ Normalize URLs so one blog under several URLs counts once. ○ Validate input: cap batch size, accept only valid http(s) URLs, and reject private or local IP ranges. ○ Protect the submission endpoint with at least one abuse-resistance measure (e.g., signed single-use tokens, proof-of-work or rate limiting). Any IP data must be stored only as a salted hash with a short expiry. ○ Document a short threat model in the README: what you defend against and what you accept. E) Offline-First Reading 
-  Fetched posts and extracted articles are cached locally (IndexedDB or localStorage). 
-  The cached timeline loads instantly, with a background refresh when online. 
-  Read state and cached articles persist across sessions. Technical Requirements: 
-  Stack: Any language and framework 
-  Hosting: Vercel, Netlify or any platform (deployment is a must) 
-  Database: Any (free tiers such as Supabase or Turso are fine) 
-  Libraries: Feed parsers and Readability-style extractors are allowed 
-  Sample Dataset: A seed list of 10–15 blogs, plus a pre-populated discovery dataset so Discover isn’t empty on demo day. Two hidden test sites will be used for evaluation.

PS-004 PrivacyLens: Building a Privacy-Preserving AI Browser Agent Background AI-powered agents can automate complex tasks such as shopping, filling forms, managing accounts, and navigating websites. However, these agents often send screenshots and webpage data to cloud-based AI models, potentially exposing sensitive information such as Aadhaar numbers, PAN, passwords, OTPs, financial details, API keys, medical records, and personal messages. This creates significant privacy and security risks. Your challenge is to build PrivacyLens, a system that enables AI agents to interact with digital interfaces intelligently while preventing sensitive user information from being exposed to external AI models. The core principle is: Compute what is sensitive locally. Reason globally only on sanitized data. Tasks A) Sensitive Information Detection Build a system that identifies sensitive information using one or more techniques: 
-  Pattern Detection: Use regular expressions and validation algorithms to detect Aadhaar, PAN, emails, phone numbers, credit/debit cards, passwords, OTPs, API keys, and other sensitive data. 
-  Structural Analysis: Inspect DOM elements, accessibility trees, metadata, or other interface representations to identify sensitive fields. 
-  AI-Based Detection: Optionally use OCR, computer vision, face detection, or Named Entity Recognition to identify contextual PII. 
-  Defense in Depth: Combine multiple techniques to reduce missed detections and false positives.
